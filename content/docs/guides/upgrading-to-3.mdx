Version 3.0 is the first release under the name **Auto Tournament**. Your players, teams, tournaments, matches, ratings, stats, servers, sign-ins and settings all move over. This page shows what changes, how to update a Docker install, and how to go back.

If you run 2.4.x for Counter-Strike 2, the short version is: back up, change one line, pull, restart. Your CS2 tournaments run the same way afterwards.

## What changes

- **The name.** MatchZy Auto Tournament (MAT) is now Auto Tournament. Menus and pages were rebuilt, so the app looks different. The tasks are the same ones.
- **CS2 is a module, not the whole app.** Counter-Strike 2 now sits in a module next to a second one, [manual reporting](/guides/manual-reporting), which runs tournaments for games the platform cannot watch. A CS2 tournament still does everything it did: servers, veto, live scores, demos and stats.
- **The licence changed.** 3.0 and everything after it are under the PolyForm Noncommercial License 1.0.0. [What that means for you](#the-licence-change) is below.
- **The CS2 plugin has a new name.** MatchZy Enhanced is now **Auto Tournament CS2**, at [github.com/Auto-Tournament/cs2-plugin](https://github.com/Auto-Tournament/cs2-plugin). It is the same plugin: it still reports itself as MatchZy in `css_plugins list`, and its settings still start with `matchzy_`. See [Auto Tournament CS2](/cs2/plugin).
- **There is a new image name.** `sivertio/auto-tournament` on Docker Hub, and `ghcr.io/auto-tournament/auto-tournament` on GitHub's registry.
- **The docs moved** from `docs.sivert.io/docs/mat` to [docs.autotournament.gg](https://docs.autotournament.gg). Old links redirect to the matching new page.

### What does not change

Nothing in your `docker-compose.yml` has to change except the image name, and even that is optional:

- The Compose service is still `matchzy-tournament`, and the containers are still `matchzy-tournament-api` and `matchzy-postgres`.
- The database is still `matchzy_tournament`, on the same volume.
- Every environment variable in your `.env` keeps its name and its meaning, and 3.0 adds no required ones. The new things you can turn on, such as game search, are configured in the app's own settings.
- The app still listens on port 3069.

### You do not have to change the image name

Every release is built once and published under all three names, so `sivertio/matchzy-auto-tournament:latest` gets 3.0 too. An install you never touch will update itself the next time you pull. Changing the name is tidier, and it is the name that will be documented from now on, but nothing breaks if you leave it.

## The licence change

Up to and including 2.4.15, Auto Tournament was MIT-licensed. From 3.0 it is under the [PolyForm Noncommercial License 1.0.0](https://github.com/Auto-Tournament/auto-tournament/blob/main/LICENSE). The source is still public, and you can still read it, change it and share your changes.

**If you run free community tournaments, LAN parties or your own server, nothing changes for you.** Personal and hobby use stays free, and so does use by schools, universities, charities and other non-profits.

**You need a licence from the author if your use is commercial.** That covers hosting Auto Tournament for other people for money, running paid-entry or ticketed events for profit, and using it inside a business. The full list, and how to ask, is on [Licensing and commercial use](/reference/licensing).

2.4.15 and earlier stay MIT. That does not change retroactively, and the old images stay on Docker Hub.

## Fixes you get on the way

Three fixes in 3.0 change how an existing install behaves. Two of them need something from you.

### Demos and event logs were being thrown away

In 2.4.x the app worked out the wrong folder for demos and event logs when running from the release image: it wrote them to `/data` inside the container instead of `/app/data`, which is the folder your `./data` volume is mounted on. Everything written there lived in the container's own writable layer, so **every update deleted every demo and event log**.

3.0 writes to the right folder, and on the first start it moves anything still lying in the old one across. But a container that is replaced loses its writable layer, so if you want the demos and logs your current container is holding, [copy them out before you update](#write-down-your-version-and-back-up). Afterwards they are on your volume and survive updates.

### Uploaded map images never appeared

Uploaded map images were written one folder above the one `/map-images` is served from, so the image was accepted and then never showed up. Worse, both folders were inside the container rather than on a volume, so whatever was there went away with the container anyway.

3.0 stores them under `./data/map-images`, on the volume you already mount, and serves `/map-images` from there. Uploads show up, and they survive updates. Images your current container is still holding are in the container, so [copy them out before you update](#write-down-your-version-and-back-up) — the map records already point at them, so they start rendering once they land on the volume.

### Match configs are no longer public

`GET /api/matches/:slug.json` is the match config your CS2 servers download, and it used to answer anyone who asked. Match slugs are easy to guess (`r1m1`, `r2m1`, …), so anyone who could reach your API could read both rosters, Steam IDs, team names, the map list and the match setup.

In 3.0 the endpoint needs either the `X-MatchZy-Token` header with your `SERVER_TOKEN`, or an admin sign-in. **Your servers need no change**: the app now puts the header on the load command it sends them, and every version of the plugin understands it. Only two things are affected:

- Loading a config URL by hand in a server console now needs `matchzy_loadmatch_url "<url>" "X-MatchZy-Token" "<SERVER_TOKEN>"`.
- Scripts or tools of your own that fetched a config anonymously now need the header or an admin token.

## Before you start

- Your install runs 2.4.x with Docker Compose, as in [Install](/getting-started/install). The upgrade is tested from **2.4.15**; if you are on an older 2.4.x, update to 2.4.15 first.
- No match is running. The app restarts.
- You have the folder with your `docker-compose.yml` and `.env`. Run every command below in that folder.
- Your CS2 servers can stay on the plugin version they have; 3.0 sets no minimum. Updating them to the latest is still a good idea, and it is a step below.

## Update

<Steps>

<Step>

### Write down your version, and back up

```bash
curl -fsS http://localhost:3069/api/settings/version
```

The answer looks like `{"success":true,"version":"2.4.15"}`. Write the version down: it is the one you go back to.

Back up the database:

```bash
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > "backups/autotournament-$(date +%F-%H%M%S).sql"
```

Check that the file in `backups/` is not empty.

Then rescue the demos and event logs your current container is holding, which are in the wrong folder and will go away with the container:

```bash
mkdir -p data
docker compose cp matchzy-tournament:/data/. ./data/
```

The trailing `/.` matters: it copies what is *inside* the old folder, so you end up with `data/demos` and `data/logs` rather than `data/data`. "No such file or directory" means there is nothing to rescue, which is fine. `./data` is where 3.0 reads them from, so whatever lands there is picked up after the update.

Do the same for uploaded map images, which 2.4.x kept in a third folder inside the container:

```bash
mkdir -p data/map-images
docker compose cp matchzy-tournament:/public/map-images/. ./data/map-images/
```

Again, "No such file or directory" just means you never uploaded any. `./data/map-images` is where 3.0 keeps them from now on, so anything you copy across is served straight away — including images 2.4.x accepted but never showed.

</Step>

<Step>

### Change the image name

Open `docker-compose.yml`, find the `image:` line of the `matchzy-tournament` service, and set the new name:

```yaml title="docker-compose.yml"
services:
  matchzy-tournament:
    image: sivertio/auto-tournament:3.0.0
```

Or make the same change from the shell, keeping a copy of the old file as `docker-compose.yml.bak`:

```bash
sed -i.bak 's#sivertio/matchzy-auto-tournament#sivertio/auto-tournament#' docker-compose.yml
```

A fixed version like `3.0.0` is worth using here, because it is what makes going back a one-line change. `sivertio/auto-tournament:latest` also works, as does `ghcr.io/auto-tournament/auto-tournament:3.0.0` if you would rather pull from GitHub.

Change **only** the image. Keep the service name, the container names, the volumes and `DB_NAME` as they are — a different database name starts an empty database.

You can also skip this step entirely and stay on `sivertio/matchzy-auto-tournament`, which gets the same 3.0 build.

</Step>

<Step>

### Pull and start

```bash
docker compose pull
docker compose up -d
```

`up -d` replaces the app container and keeps the database volume.

</Step>

<Step>

### Watch the first start

```bash
docker compose logs -f matchzy-tournament
```

The first start on your existing database does three things, in this order, and each one logs a line:

1. **Moves the stray demos and logs** into `/app/data`: `[data-dir] Migrated N item(s) out of the legacy data directory`.
2. **Adds the new tables and columns** — accounts, linked accounts, team memberships, match reports, custom stat fields and the game catalogue. Nothing existing is dropped, renamed or rewritten.
3. **Runs two backfills**, which announce themselves as `Applied migration 2026-09-22-linked-accounts-backfill` and `… team-members-backfill`. The first records the Steam and Discord accounts your database already knows in the new accounts table; the second turns every team roster into team memberships. Both only add rows.

Each backfill is recorded in a `schema_migrations` table, runs once, and is written in the same transaction that records it — so a restart in the middle cannot leave one half-applied, and later starts skip them. If one fails it is logged and retried on the next start.

Press `Ctrl+C` when the log says the server has started.

</Step>

<Step>

### Check that it works

```bash
curl -fsS http://localhost:3069/api/settings/version
curl -fsS http://localhost:3069/health
```

The version must be 3.0 or newer. Then open the app, sign in, and check that your teams, players, ratings and past matches are there.

</Step>

<Step>

### Update the CS2 plugin on your servers

Put the same, latest version of Auto Tournament CS2 on every server. With CS2 Server Manager:

```bash
sudo csm update-plugins
```

Without it, see [Update the CS2 plugin](/cs2/plugin/install#update). Then open the **Servers** page, click **Refresh Status**, and **Retry** any server that is not set up.

</Step>

<Step>

### Promote captains, if you want manual reporting

Only needed if you are going to run a tournament through [manual reporting](/guides/manual-reporting). 2.x had no idea who captains a team, so the upgrade makes everyone a plain member and no captains. Reporting a result is a captain's job, so pick one per team on the team page before the tournament starts.

</Step>

<Step>

### Update your links

The docs are at [docs.autotournament.gg](https://docs.autotournament.gg) and the source is at [github.com/Auto-Tournament/auto-tournament](https://github.com/Auto-Tournament/auto-tournament). Old links to either redirect, but bookmarks and pinned Discord messages are worth fixing.

</Step>

</Steps>

## Go back to 2.4.15

3.0 only adds to the database — no table or column is dropped, renamed or rewritten — so 2.4.15 starts again on a database 3.0 has migrated, shows the same data, and can still be written to. That was tested by upgrading a 2.4.15 install to 3.0 and then booting 2.4.15 back onto the same database.

Anything created only in 3.0, such as a match report or a team captain, is invisible to 2.4.15. It stays in the database, and comes back if you move to 3.0 again.

<Steps>

<Step>

### Set the old image back

```yaml title="docker-compose.yml"
services:
  matchzy-tournament:
    image: sivertio/matchzy-auto-tournament:2.4.15
```

If you used the `sed` command above, `mv docker-compose.yml.bak docker-compose.yml` puts the old file back; then pin `2.4.15` in it, so a later `pull` does not fetch 3.0 again through `latest`.

</Step>

<Step>

### Pull and restart

```bash
docker compose pull
docker compose up -d
```

Check the version:

```bash
curl -fsS http://localhost:3069/api/settings/version
```

</Step>

<Step>

### Restore the backup, if something is wrong

If 2.4.15 does not start, or your data looks wrong, load the backup you made into an empty database:

```bash
docker compose stop matchzy-tournament
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"' < backups/autotournament-YYYY-MM-DD-HHMMSS.sql
docker compose up -d
```

Use your own backup's file name. `dropdb` deletes everything, including whatever was written after the backup was taken.

</Step>

</Steps>

## If something goes wrong

- **The app will not start.** `docker compose logs matchzy-tournament` usually names the cause. A missing value in `.env` and a database it cannot reach are the two common ones.
- **Your data looks empty.** Almost always a changed `DB_NAME`, or a volume that was recreated. Check that `docker-compose.yml` still points at the same database and the same volume as before.
- **A server shows a plugin version mismatch.** Update the plugin on every server to the same version. See [Server health warnings](/reference/servers-health).
- **Anything else.** [Troubleshooting](/reference/troubleshooting), or ask on [Discord](https://discord.gg/n7gHYau7aW).
